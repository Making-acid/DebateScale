# DebateScale 架构原则

## 1. 仓库是容器，不是共享内核

DebateScale 使用单仓库管理多个独立系统与平台接入，但仓库本身不提供一个要求所有系统依赖的“公共核心”。每个系统必须能够在不安装其他系统的情况下独立开发、测试、安装、运行和交付。

## 2. 系统自治边界

每个系统自行拥有：

- 提示词和研究方法；
- 领域模型与状态结构；
- 调度、预算和停止机制；
- 模型、搜索、网页读取和媒体处理适配；
- 检查点、输出协议和测试；
- 该系统自己的运行引擎；
- 标准本地启动器和必要的开发、验证界面。

禁止：

- 从另一个系统的内部目录直接导入代码；
- 通过共享提示词或共享状态模型让两个系统隐式绑定；
- 为了减少少量重复而提前抽取公共运行时；
- 让某个前端的数据结构成为所有系统的事实标准。

当两个系统恰好需要相似能力时，默认各自实现和维护。只有在它被证明是独立产品、拥有稳定契约并可被任何外部调用者使用时，才考虑把它作为单独适配器或服务发布；这不构成系统共享资产。

## 3. 平台接入边界

`integrations/` 中的 ChatGPT、Coze、DSH、WorkBuddy、MCP 或其他宿主接入只面向系统公开接口。接入层负责必要的协议转换、权限声明和用户交互适配，不读取系统内部检查点，也不依赖内部提示词或存储格式。

目标平台不一定拥有插件市场。因此每个接入目录都必须能从仓库直接使用，并尽量缩减为一份说明、少量配置和必要的薄适配代码。增加或删除某个系统，不应迫使其他系统修改。

## 4. 本地启动器地位

标准本地 Web 工作台是系统完整交付的一部分，可以保留在系统包内。它不是唯一运行方式，也不能成为系统内部能力的唯一入口。接入其他平台时，通常应当删去不适用的本地界面或配置，并通过很小的公开表面调用同一个完整系统，而不是为平台重新实现系统。

## 5. 当前目录约定

```text
systems/<system-name>/      完整独立系统及其专属资产、启动器、测试和文档
integrations/<target>/      面向某个宿主的说明、配置和必要薄适配
docs/                       跨项目的产品说明与架构决策
```

新系统进入仓库时，应先证明它可以独立运行，再按实际需求建立平台接入；不得以复用当前深度研究系统内部代码作为起点，也不提前创建没有被真实平台验证的接入框架。
