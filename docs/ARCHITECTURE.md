# DebateScale 架构原则

## 1. 仓库是容器，不是共享内核

DebateScale 使用单仓库管理多个引擎与接入插件，但仓库本身不提供一个要求所有引擎依赖的“公共核心”。每个引擎必须能够在不安装其他引擎的情况下独立开发、测试、安装和运行。

## 2. 引擎自治边界

每个引擎自行拥有：

- 提示词和研究方法；
- 领域模型与状态结构；
- 调度、预算和停止机制；
- 模型、搜索、网页读取和媒体处理适配；
- 检查点、输出协议和测试；
- 该引擎专属的开发或验证界面。

禁止：

- 从另一个引擎的内部目录直接导入代码；
- 通过共享提示词或共享状态模型让两个引擎隐式绑定；
- 为了减少少量重复而提前抽取公共运行时；
- 让某个前端的数据结构成为所有引擎的事实标准。

当两个引擎恰好需要相似能力时，默认各自实现和维护。只有在它被证明是独立产品、拥有稳定契约并可被任何外部调用者使用时，才考虑把它作为单独适配器或服务发布；这不构成引擎共享资产。

## 3. 插件边界

`plugins/` 中的 ChatGPT、DSH、MCP 或其他 Harness 接入只面向引擎公开接口。插件负责协议转换、权限声明和用户交互适配，不读取引擎内部检查点，也不依赖内部提示词或存储格式。

一个插件可以分别适配多个引擎，但适配层必须明确分开。增加或删除某个引擎，不应迫使其他引擎修改。

## 4. 前端地位

前端是引擎的消费者，不是项目核心。当前 Web 工作台属于验证工具；未来可以被重写、替换或与 ChatGPT、DSH 等接入并存。引擎的完整能力必须通过公开接口表达，不能只存在于某个界面中。

## 5. 当前目录约定

```text
engines/<engine-name>/   独立引擎及其专属资产、测试和文档
plugins/<target>/        面向某个宿主的接入实现
docs/                    跨项目的产品说明与架构决策
```

新引擎进入仓库时，应先证明它可以独立运行，再为它建立插件适配；不得以复用当前深度研究引擎内部代码作为起点。
