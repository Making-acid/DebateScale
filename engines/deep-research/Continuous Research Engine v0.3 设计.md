# Continuous Research Engine v0.3：双边立论型深度研究

## 1. 引擎的位置

CRE 是一个“初次接触辩题”阶段使用的思想实验引擎。它不是负责寻找极端思想实验的循环对抗引擎，也不是把搜索结果堆给用户的资料聚合器。

它的任务是：

1. 让 A、B 两个模型分别固定在互相冲突的立场上。
2. 通过广泛搜索与深读，理解各自立场可以怎样成立。
3. 将知识组织成可承担证明责任的论点，而不是零散材料。
4. 让双方针对对方当前立论进行基础驳论，用于暴露事实错误、推理断点和范围过度扩张。
5. 修复可修复的错误，保留真正不可调和的价值分歧。

因此，这个引擎的核心动词不是“讨论”，而是“证明”：每个模型都要尽力证明自己的立场成立，并证明对方的论证为什么不成立或只能在更小范围内成立。

## 2. 主产品不是文章，而是可用的论证系统

引擎不以“写出漂亮的立论稿”为必要目标。它产出三类一等对象：

### Argument：当前立论

每个论点必须明确包含：

- 主张：究竟要证明什么。
- 证明责任：这个主张要成立，最低需要证明什么。
- 判准：使用什么标准判定双方胜负或价值高低。
- 论证链：从机制、条件到结果的至少两步推理。
- 证据：已深读材料中哪些发现支持了哪一步。
- 影响：如果主张成立，对辩题判断有什么意义。
- 成立边界：它在什么条件下成立，不宣称什么。
- 薄弱处与防守：对方最可能击中哪里，当前如何回答。

Argument 有版本号。任何修改都会保留旧版快照，使驳论始终能指向它当时攻击的具体文本。

### Rebuttal：可以被人理解的攻击

驳论不应只是“请修复 issue_017”这类内部工单。每条驳论必须说清：

- 它理解的对方论证是什么。
- 它攻击的是事实、因果、概念、判准、范围还是权重。
- 具体的断点在哪里。
- 如果攻击成立，为什么会动摇对方的结论。
- 对方最可能怎样回应。
- 经过修改后，这条攻击是已回答、仍存活还是已失效。

### EvidenceRecord：深读后的证据账本

搜到 URL 不等于完成研究。证据记录必须绑定已读取的来源，并记录：它要支持或削弱什么命题、研究发现、方法、局限、与论点的关系以及可追溯来源。

## 3. 深度研究如何“深”

深度不依靠提示词中写一句“请深入研究”，而由工具链和收束门槛共同强制。

### 广度

每一方都要主动发现足够多的来源。生产默认值是每方至少 24 个来源，而不是全局共用 6 个结果就结束。查询应覆盖概念史、理论、经验研究、机制、案例、比较情形、失败案例、反方证据和相邻学科。政策辩题还需要制度现状、利益相关者、执行机制、成本、风险、替代方案和外部经验。

### 深度

发现来源后，模型要调用全文读取工具，不能只根据搜索摘要下结论。生产默认值是每方至少深读并形成 12 条可用证据记录。证据必须被绑定到具体论点的具体证明任务，否则只是资料，不是论证。

### 自主思考

前人的说法是原材料，不是引擎的结论。模型必须先拆解辩题的定义、量词、比较对象、时间范围、判准和双方证明责任，再自主提出论证组合。搜索计划从证明义务生成，而不是从“有什么相关信息”生成。

### 不能把可完成的工作退回给用户

一个高价值证明义务只有三种合法结局：已经完成；经过研究证明不可行并调整论点；有具体的外部阻塞而无法继续。只要还能通过搜索、深读或推理继续完成，就不得把它包装成“未来研究方向”后停止。

### 搜索策略是条件式方法，不是固定清单

模型每次搜索都要先明确两个很短的信息：这次搜索准备修补哪一项证明缺口，以及为什么当前查询方式适合这个缺口。引擎提供可选择的策略，例如术语与版图发现、原始来源追溯、机制搜索、经验检验、反证与边界搜索、冲突解释和查询修复，但不要求模型机械地依次执行全部策略。

当领域仍然陌生时可以先宽搜；当概念和候选机制已经明确时，应转向精确的来源搜索。已有大量支持材料时，应寻找反例、无效结果和范围限制。可信材料相互冲突时，应先检查定义、样本、方法、时间与适用范围。结果噪声较大时，应改变来源类型、术语、语言、地区、群体或方法等有意义的查询维度，而不是仅仅换一种句式重复搜索。

搜索计划采用滚动方式：只保留当前少数几项高价值查询，每批结果返回后先判断“什么发生了变化”，再决定深读、转向、收窄或停止该分支。搜索工具中的策略提示应与系统级研究原则保持一致，使模型在真正采取行动时仍能获得方法指导。

### 提示词与执行逻辑分离

研究身份、阶段方法、公共研究纪律、搜索工具策略和结果反馈以独立 Markdown 资源保存在 `src/cre/prompts/`。Python 只负责按照当前阶段装配提示词、注入辩题和立场，并执行结构化工具调用。这样可以单独审阅、比较和迭代提示词，也便于未来由不同前端、插件或 Harness 复用同一引擎。

提示词资源属于引擎能力的一部分，会随 Python 包一同分发。修改资源后应重启运行中的服务，避免已有进程继续使用缓存的旧提示词。

### 可审计过程与预算分账

前端可以订阅引擎的结构化进度事件，展示模型当前处于哪个 Pass、选择了哪些行动、搜索的目的与策略、实际查询、候选来源返回、来源深读、证据登记、论点修改、质量门槛和预算状态。这里展示的是可验证的外部行动和状态变化，不展示或伪造模型的私有思维链。

预算区分三类活动：模型轮次与 Token、有效的外部研究调用、失败调用缓冲。本地的 Research Map、EvidenceRecord、Argument 和 Rebuttal 更新会被记录为过程事件，但不再消耗外部研究调用额度，因为这些动作是同一次模型响应中的本地状态写入。搜索或读取失败使用单独且有上限的缓冲，避免偶发网络失败吞掉全部有效研究额度，也避免无限重试。

### 分层证据漏斗与滚动上下文

Pass One 不再把“搜到的内容”直接等同于长期研究记忆。每条路线依次经过：证明缺口诊断、宽候选检索、确定性相关性与重复筛查、带明确目的的来源深读、EvidenceRecord 证据卡、Argument/ResearchMap 修订。候选搜索结果可以被丢弃；只有检查过的证据卡和因此发生变化的证明链进入长期上下文。活跃证明任务限制为最多五项，模型需要完成、合并或关闭旧任务后才能继续开枝，防止用分支数量冒充研究广度。

引擎的长期记忆是结构化黑板，不是完整聊天历史。每个模型轮次只携带压缩后的当前论点、证据卡、优先来源短表、活跃证明任务，以及上一轮尚待消费的工具结果；消费后即从对话窗口移除。来源全文继续保存在 Source Pool，深读工具根据当前证明目的和 focus terms 返回相关段落。前端分别显示累计 Token、当前输入上下文估算和滚动压缩次数，使“单次上下文过大”与“长任务累计成本”可以被区分。

同一 URL 对某一立场发生永久性访问失败（如 401/403/404）后，会被标记为该方不可直接读取并从其候选短表移除；模型必须寻找开放获取副本、仓储版本、摘要索引或替代一手来源，不能重复烧预算。两方并行 Pass 采用故障隔离：一方达到预算或供应商失败时，另一方仍可完成并持久化检查点；再次恢复时只补跑未完成的一方。

## 4. 运作循环

### Pass One：独立立论

A、B 在隔离的上下文中完成辩题拆解、研究地图、来源发现、深读、证据记录和立论组合。双方都必须形成至少 3 个结构完整的核心论点。

### Collision：基础互驳

双方可以看到对方当前论点。每方至少形成 2 条完整驳论，优先寻找能够改变论点成立性的事实错误、概念滑动、因果跳跃、外推过度和权重错位。这一阶段的目的是帮助对方暴露普通比赛中会被击穿的缺口，不是制造极端对抗。

### Continuous：立论修复

被驳的一方通过补充证据、修正因果链、收窄主张、改变权重或撤回失败论点来回应。另一方检查修复后的新版本。这个循环直到当前版本不再存在未处理的有效攻击。

### Stability Check：稳定审计

模型的“我觉得已经完成”不构成停止理由。只有同时满足以下条件才能进入人工复核：

- 双方达到来源发现与证据深读的数量下限。
- 双方达到完整论点与驳论数量下限。
- 所有非撤回论点已经完成证明结构，并被标记为可防守。
- 没有针对当前论点版本的未回答驳论。针对旧版本的驳论只留在历史中。
- 没有未完成且可继续搜索的高价值证明义务。
- 没有尚未处理的高优先级事实或逻辑错误。

达到最大循环数也不得伪装成稳定；引擎应进入人工复核，并告知用户尚未完成的证明义务。

## 5. 人类输出空间

界面默认展示“当前成果”，而不是模型对话流。

1. **当前成果**：双方当前有效论点及最重要攻防。
2. **双方立论**：可逐条展开证明责任、论证链、证据、边界和防守。
3. **攻防要点**：以人类可读的方式展示攻击对象、断点、影响和当前结果。
4. **证据与来源**：区分“发现过”与“已深读并用于论证”。
5. **推演历史**：用户主动点击后才看到论点旧版本、内部修复记录和各 Pass 变化。

导出文档使用同样的顺序：当前立论→当前驳论→证据账本→推演历史附录。用户不需要阅读内部工单，才能理解引擎到底研究出了什么。

## 6. 与循环对抗引擎的边界

CRE 要完成“广泛理解—构建基础立论—去除明显错误”。它的互驳是为了打磨立论，不追求极限杀伤性。

后续的循环对抗引擎可以把 CRE 的稳定论证系统作为输入，使用树状分支反复逼问，寻找让对方真正感到难以处理的思想实验。两者是先后衔接的插件，不应在当前引擎内混为一个目标。
